Functions and automation in coding

Up until now, we’ve exclusively used pre-built functions in our R code. These functions come from different packages, and were written to improve our efficiency by automating very common tasks that we need to do, things like plotting, wrangling, and modeling data. That’s the whole purpose behind functions: they take code that is used regularly and wrap it into a repeatable, simple unit that we can easily deploy across tasks, files, and even projects. For example, imagine we have a dataset of insect abundance across 12 sites:

# A tibble: 1,200 × 5
   site   trap_id date       taxon   abundance
   <chr>  <chr>   <date>     <chr>       <int>
 1 Site_1 Trap_1  2026-06-01 Beetles        12
 2 Site_1 Trap_1  2026-06-01 Flies          17
 3 Site_1 Trap_1  2026-06-01 Bees            7
 4 Site_1 Trap_1  2026-06-01 Ants           16
 5 Site_1 Trap_1  2026-06-01 Spiders         5
 6 Site_1 Trap_1  2026-06-15 Beetles         5
 7 Site_1 Trap_1  2026-06-15 Flies          13
 8 Site_1 Trap_1  2026-06-15 Bees            5
 9 Site_1 Trap_1  2026-06-15 Ants           17
10 Site_1 Trap_1  2026-06-15 Spiders         3
# ℹ 1,190 more rows

And we want to generate some summary statistics for each site, such as total abundance, species richness, and the number of distinct samping events. We could do this by repeatedly using the same block of code, filtering to each site:

# Summarize Site 1
site_1_summary <- insect_data |>
  filter(site == "Site_1") |>
  summarise(
    total_abundance = sum(abundance),
    richness = n_distinct(taxon),
    sampling_events = n_distinct(date)
  )

# Summarize Site 2
site_2_summary <- insect_data |>
  filter(site == "Site_2") |>
  summarise(
    total_abundance = sum(abundance),
    richness = n_distinct(taxon),
    sampling_events = n_distinct(date)
  )

# Summarize Site 3
site_3_summary <- insect_data |>
  filter(site == "Site_3") |>
  summarise(
    total_abundance = sum(abundance),
    richness = n_distinct(taxon),
    sampling_events = n_distinct(date)
  )

# And so on for each of the 12 sites...

This copying and pasting approach works, but is slow, error prone, and can make a lot of extra work for us if we need to change something or add an additional summary statstic: we’d need to make that change twelve times. This is very inefficient! Instead, we can package our code as a function so that we can easily re-use the code and minimize the total amount of code that we need to write (and therefore, maintain!):

# Create a function called `summarize_site` that we can use
summarize_site <- function(data, site_name) {
  data |>
    filter(site == site_name) |>
    summarise(
      total_abundance = sum(abundance),
      richness = n_distinct(taxon),
      sampling_events = n_distinct(date)
    )
}

We can then call our function, specify the arguemnts, and get our summaries! All in 3 lines of code instead of 21. 1/7 of the space!

# Summarize Site 1
summarize_site(insect_data, "Site_1")
# A tibble: 1 × 3
  total_abundance richness sampling_events
            <int>    <int>           <int>
1             884        5               5
# Summarize Site 2
summarize_site(insect_data, "Site_2")
# A tibble: 1 × 3
  total_abundance richness sampling_events
            <int>    <int>           <int>
1             806        5               5
# Summarize Site 3
summarize_site(insect_data, "Site_3")
# A tibble: 1 × 3
  total_abundance richness sampling_events
            <int>    <int>           <int>
1             871        5               5

Functions

So, as we touched on above, we want to write functions anytime we are repeatedly using a bit (or a lot) of code to do a common task. By doing this, we can create code that:

  1. has an evocative name that makes our code easier to understand
  2. has only one place where we need to make changes
  3. eliminates (or significantly reduces) the chance of making a mistake
  4. makes it easier to re-use our code from project-to-project
TipWhen to make a function?

If you find yourself copying and pasting code more than twice, that’s a good indication you would benefit from writing a function!

Let’s build a function

Let’s walk through turning copy-and-paste code into a re-usable function!

df <- tibble(
  a = rnorm(5),
  b = rnorm(5),
  c = rnorm(5),
  d = rnorm(5),
)

df |>
  mutate(
    a = (a - min(a, na.rm = TRUE)) /
      (max(a, na.rm = TRUE) - min(a, na.rm = TRUE)),
    b = (b - min(a, na.rm = TRUE)) /
      (max(b, na.rm = TRUE) - min(b, na.rm = TRUE)),
    c = (c - min(c, na.rm = TRUE)) /
      (max(c, na.rm = TRUE) - min(c, na.rm = TRUE)),
    d = (d - min(d, na.rm = TRUE)) /
      (max(d, na.rm = TRUE) - min(d, na.rm = TRUE)),
  )
#> # A tibble: 5 × 4
#>       a       b     c     d
#>   <dbl>   <dbl> <dbl> <dbl>
#> 1 0.339  0.387  0.291 0
#> 2 0.880 -0.613  0.611 0.557
#> 3 0     -0.0833 1     0.752
#> 4 0.795 -0.0822 0     1
#> 5 1     -0.0952 0.580 0.394

In the above code, we’re scaling randomly pulled values from a normal distribution to values between 0 and 1 within each variable. Nothing too fancy, but if we want to do this across all of our numeric variables, we have to repeat bunch of code. Seems like a perfect spot to use a function! To start, we need to look at our code and identify the parts that are constant and the parts that vary:

Here’s the stuff inside the mutate call pulled out to identify the repeating parts:

(a - min(a, na.rm = TRUE)) / (max(a, na.rm = TRUE) - min(a, na.rm = TRUE))
(b - min(b, na.rm = TRUE)) / (max(b, na.rm = TRUE) - min(b, na.rm = TRUE))
(c - min(c, na.rm = TRUE)) / (max(c, na.rm = TRUE) - min(c, na.rm = TRUE))
(d - min(d, na.rm = TRUE)) / (max(d, na.rm = TRUE) - min(d, na.rm = TRUE))

Each line here is constant, what varies is the variable (haha) that we are rescaling. Excellent!

(█ - min(█, na.rm = TRUE)) / (max(█, na.rm = TRUE) - min(█, na.rm = TRUE))

Now that we have that identified, we need to do three things:

  1. Choose a name for our function: We’ll use rescaler since the function…well…it rescales things.
  2. Define the arguments: These are the bits and bobs that vary across the function calls and are passed into our function to be operated on. We’ll use x as our argument.
  3. Write the function body: i.e., the code that’s repeated each time
# The general format/syntax of a new function
name <- function(arguments) {
  body
}

# When applied to our example, our function looks like this:
rescaler <- function(x) {
  (x - min(x, na.rm = TRUE)) / (max(x, na.rm = TRUE) - min(x, na.rm = TRUE))
}

In this, whatever we pass in for x (in this case, any vector of numbers), will be substituted in for x in our function and evaluated accordingly. Let’s test it:

# Specify numerical vector in advance
my_vector <- c(4, 6, 11, 45, 20, 6)

rescaler(x = my_vector)
[1] 0.00000000 0.04878049 0.17073171 1.00000000 0.39024390 0.04878049
# Specify numerical vector in the function call
rescaler(x = c(4, 6, 11, 45, 20, 6))
[1] 0.00000000 0.04878049 0.17073171 1.00000000 0.39024390 0.04878049

Vector functions

Vector functions are like the one that we just developed above: they’re functions that take one or more vectors and return a vector result. These are great functions to build and use inside other functions like dplyrs many verbs (e.g., mutate() and filter()) as they return an output of the same length as the input.

Data frame functions

Data frame functions are useful for when yiou want to repeat dplyr verbs many times. Data frame functions work like dplyr verbs: they take a data frame (or tibble) as input, and return data frames. Writing these functions is very similar to vector functions, but there’s one notable difference: embracing.

Imagine that we want to create a simple data frame function that calculates a group-based mean:

grouped_mean <- function(df, group_var, mean_var) {
  df |>
    group_by(group_var) |>
    summarize(mean(mean_var))
}

Here, we pass our function 3 arguments: the data frame we want to work on (df), the grouping variable (group_var) and the variable we want to calculate the mean for (mean_var). Great! Let’s try and use this on our insect data frame above:

grouped_mean(
  df = insect_data,
  group_var = site,
  mean_var = abundance
)
Error in `group_by()`:
! Must group by variables found in `.data`.
✖ Column `group_var` is not found.

What’s up? R is telling us that the groupin variables don’t exist. How strange. The issue here is that dplyr is using tidy evaluation to allow us to refer to the names of hte variables without any special treatment. This means that when we use our grouped_mean() function, group_by() and summarize() are looking for variables literally named group_var and mean_var – the names of our arguments, rather than the values we are passing in.

We can get around this by embracing 🤗 our variables in the function call. Now, our variable var becomes {var}. This tells dplyr to look at the value inside the argument, not the argument name itself:

grouped_mean <- function(df, group_var, mean_var) {
  df |>
    group_by({{ group_var }}) |> # We embrace group_var
    summarize(mean({{ mean_var }})) # We embrace mean_var
}

grouped_mean(
  df = insect_data,
  group_var = site,
  mean_var = abundance
)
# A tibble: 12 × 2
   site    `mean(abundance)`
   <chr>               <dbl>
 1 Site_1               8.84
 2 Site_10              9.16
 3 Site_11              8.87
 4 Site_12              9.37
 5 Site_2               8.06
 6 Site_3               8.71
 7 Site_4               8.58
 8 Site_5               9.06
 9 Site_6               9.05
10 Site_7               8.54
11 Site_8               8.43
12 Site_9               8.66
TipWhen to use data frame functions?

There are many use-cases, but if you frequently calculate the same summary stats about datasets, you may consider wrapping that up as a helper function that you can re-use.

Plot functions

Plotting functions are basically the same as data frame functions, with the only difference being that they take in a data frame but spit out a ggplot object(s)! Here, we still need to use embracing for any data frame variables that we want to pass in as arguments.

Iteration

Iterating is a bit different than functions, in that iteration is just about repeatedly doing some action on different objects. Functions can help us iterate, but functions don’t necessarily iterate. We’ve had some implicit experience with iteration already: using things like facet_wrap() in plots, or group_by() in data summaries and mutations.

In the tidyverse world, one very easy way to iterate is to use the across() function to perform the same operation across many iterations. For example:

# this breaks our rule of copying and pasting more than twice!
df |>
  summarize(
    n = n(),
    a = median(a),
    b = median(b),
    c = median(c),
    d = median(d),
  )

# it can instead become...
df |>
  summarize(
    n = n(),
    across(a:d, median),
  )

The across() function has 3 important arguments that you’ll need to use:

  1. .cols: specifices the columns you wish to iterate over
  2. .fns: specifies the functions you want to apply
  3. .names: gives you additional control over naming the output columns

We can use our helper functions we learned about way back in weeks 5 and 6 of data wrangling to power-up our use of across(). For example we can use the where() function to grab columns based on their type:

  • where(is.numeric) selects all numeric columns.
  • where(is.character) selects all string columns.
  • where(is.Date) selects all date columns.
  • where(is.POSIXct) selects all date-time columns.
  • where(is.logical) selects all logical columns.

These can be combined with boolean algebra and other conditionals to create more complex filterations:

  • !where(is.numeric) selects all non-numeric columns
  • starts_with("a") & where(is.logical) selects all logical columns whose name starts with “a”.

for loops

At a foundational level, the for loop is the most basic way to perform iterations in any programming language, and R is no exception. Here, we’ll touch on the very basics of for loops, mostly because I rarely use them. The Tidyverse contains so many functions that basically allow us to forgo writing for loops.

for (i in 1:5) {
  print(i)
}
[1] 1
[1] 2
[1] 3
[1] 4
[1] 5

This is the most basic syntax of a for loop. We can break it into parts:

  • for tells r to start a loop
  • i is the iterator; a temporary variable that changes with each iteration (controlling flow)
  • 1:5 is the sequence of values over which we want to iterate
  • { } contains the code that gets excuted for each iteration.

Let’s make our loop do something more useful than just print 1 through 5!

# Insect counts at five sampling sites
insect_counts <- c(12, 8, 15, 23, 10)

# Loop through each sampling site
for (i in 1:5) {
  # Double the observed count
  adjusted_count <- insect_counts[i] * 2

  print(adjusted_count)
}
[1] 24
[1] 16
[1] 30
[1] 46
[1] 20

Notice anything new here? our i is doing more than just acting as an iterator. We’re also using it to access the corresponding element of the vector over which we are iterating (i.e., an index value). This is common practice, and we’ll often use that iterator to specify position in:

  • a vector named vec: for (i in length(vec)) { code here }
  • a data frame named df: for (in in 1:nrow(df)) { code here }
Important

I suggest avoiding for loops as much as you can and instead finding a Tidyverse alternative way to iteration. The reason behind this is efficiency: the folks writing Tidyverse code are way better at writing code that is computationally efficient and fast. When we write our own loops, well…take a look below at what can happen!

A short word on efficiency

There are more or less efficient ways to write our functions and iterate through data. This takes time to fully get used to and figure out. But in general there are two things you can optimize loops and other iteration tasks:

  1. Do as much as you can outside the loop: every line of code inside a for loop will be run many, many times. If it only needs to be run once, place it outside of the loop to avoid repetition.
  2. Ensure that storage objects are large enough to contain all results: For example, if our ending vector from our loop will have 1000 values, start by first creating that storage vector rather than iteratively adding to it. This is best shown with an example:
system.time({
  output <- rep(NA, 1000000)
  for (i in 1:1000000) {
    output[i] <- i + 1
  }
})
##   user  system elapsed
##  0.026   0.001   0.027

system.time({
  output <- NA
  for (i in 1:1000000) {
    output[i] <- i + 1
  }
})
##     user   system  elapsed
## 1689.537  560.951 2249.927

Here, the first loop stores values as object that begins with the length of one million, the total size of our eventual output. the second loop begins with an object of length 1 and then expands it up to a length of one million. The result? The first loop takes ~ 3 tenths of a second to run, while the second takes almost 38 minutes to run (this depends A LOT on your computer’s spec, on my machine with a boat load of RAM this happens much faster, but the point is it can take a very long time if who ever is running your code has an older computer, which many folks do!).

We’ll now walk through three specific examples of common tasks that we can iterate in R to save time and make our code more efficient and less error-prone.

Common example: Reading multiple files using map()

One common way that we need to iterate is if we have multiple data files that we want to import into R. We could just do it the ol’ copy and paste way:

data2019 <- readxl::read_excel("data/y2019.xlsx")
data2020 <- readxl::read_excel("data/y2020.xlsx")
data2021 <- readxl::read_excel("data/y2021.xlsx")
data2022 <- readxl::read_excel("data/y2022.xlsx")

But that gets tedious fast especailly have we have potentially dozens or even hundreds of files to import. We’ll start by first just getting a list of the files that we want to import:

paths <- list.files(
  "data/bird_survey_data",
  pattern = "[.]xlsx$",
  full.names = TRUE
)
paths
