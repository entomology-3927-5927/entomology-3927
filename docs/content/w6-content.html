Combining data: *_join functions

Most experiments or observational studies involve the collection of more than one dataset. More often than not, we need to find ways to combine multiple sources of data (i.e., tibbles or data frames) into a single unit, either by appending observations or columns. Sometimes, we can just stick the pieces together directly (i.e., binding rows or columns: bind_rows() or bind_cols()), but typically we need to make connections by matching values between our data frames. We can do that in two ways:

  1. Mutating joins where we add new variables to a data frame from matching observations in another
  2. Filtering joins where we filter observations from one data frame based on whether or not they match an observation in another.

We make joins like these happen by using keys: variables that allow you to link two data sets together (i.e., like a lock and key link to open a door). There are types of keys:

  1. Primary key: a variable or set of variables that uniquely identifies each observation. When more than one variable is needed, the key is called a compound key. For example, in the below dataset, the sample_id column represents a primary key; a unique value for each observation that we could use to match other data. If we needed to to match against sample_id and patient_id, that would be a compound key.
# A tibble: 4 × 4
  sample_id patient_id tissue_type batch  
  <chr>     <chr>      <fct>       <fct>  
1 SAMP_001  PT_A       Control     Batch_1
2 SAMP_002  PT_A       Tumor       Batch_1
3 SAMP_003  PT_B       Control     Batch_2
4 SAMP_004  PT_B       Tumor       Batch_2
  1. Foreign key: a variable or set of variables that corresponds to the primary key in another table. It’s the “lock” to the “key” in your primary dataset. Typically, primary and foreign keys have the same or almost the same name. Implicit in this, is that the varible names for primary and foreign keys should have the same meaning in each dataset.
Tip

It’s important to check that your primary keys uniquely identify each observation. The easy way to do this is to use count() to ensure that there are no primary keys where n > 1.

The joining functions

dplyr has 6 joining functions; 4 mutating, and 2 filtering joins:

Join Function Type Behavior / Use Case Simple Example Code
left_join(x, y) Mutating Keeps all rows from x and matches rows from y. Fills missing values with NA. Most common join type in bioinformatics metadata handling. left_join(counts, metadata, by = join_by(sample_id_))
right_join(x, y) Mutating Keeps all rows from y and matches rows from x. Fills missing values with NA. Useful when appending existing metrics to a newly filtered target table. right_join(counts, target_samples, by = join_by(sample_id))
inner_join(x, y) Mutating Keeps only rows present in both x AND y. Drops unmatched rows from both sides. Use when you strictly require complete observations across both datasets. inner_join(genes, annotations, by = join_by(ensbml_id))
full_join(x, y) Mutating Keeps all rows from both x and y. Unmatched pairs on either side receive NA. Use to combine multi-batch assays without losing any samples or features. full_join(batch1_df, batch2_df, by = join_by(patient_id))

Join keys

By default, left_join(), the most common that we use, will use all variables that appear in both data frames as a compound join key – this is a relatively safe way to ensure that we’re matching only unique values. For example:

# Dataset 1: Species survey counts at monitoring sites
species_surveys <- tibble(
  survey_id   = paste0("SURV_", 1:5),
  site_code   = c("SITE_A", "SITE_A", "SITE_B", "SITE_C", "SITE_D"),
  year = c(2021, 2022, 2021, 2022, 2023),
  species     = c("Salmo trutta", "Salmo trutta", "Cottus gobio", "Salmo trutta", "Rana temporaria"),
  abundance   = c(14, 8, 32, 19, 5)
)

# Dataset 2: Environmental logger metadata
site_env <- tibble(
  site_code = c("SITE_A", "SITE_B", "SITE_C", "SITE_E"),

  habitat     = c("Riffle", "Pool", "Riffle", "Run")

# Join datasets using implict keys (here, site_code and year)

Filtering joins

Filtering joins….well…they filter! It’s a slightly different approach than using the filter() function that we practiced with last week, and here we’re using observations in another, separate dataset as our filtering conditions rater than a set of logical rules that we specify in our filter() call. There are two types: semi_join() and anti_join()

Join Function Type Behavior / Use Case Simple Example Code
semi_join(x, y) Filtering Keeps rows in x that have a match in y. Does not add columns from y or duplicate rows in x. Use to filter a large dataset using a list of target identifiers. semi_join(all_genes, sig_gene_list, by = join_by(ensbml_id))
anti_join(x, y) Filtering Keeps rows in x that DO NOT have a match in y. Does not add columns from y. Use for quality control to identify missing samples or failed assays. anti_join(raw_samples, QC_passed, by = join_by(sample_id))
Tip: finding implicit missing data with anti_join()

anti_join() is really useful for finding missing values that are implicit. For example, we could find rows that are missing from our species_surveys data by looking for sites that don’t have a matching site_id according to the site_env data.

Non-equi joins

Last but not least, we have non-equi joins. These utilize the same functions as our mutating and filtering joins, but we will utilize non-equivalent conditions to make our matches. For example:

  • Equi join: left_join(x, y, by = join_by(key == key))
  • Non-equi join: left_join(x, y, by = join_by(key >= key))

There are four typres of non-equi join that are most helpful: 1. Cross joins match every pair of rows. This can be useful for creating all possible combinations of your variables. 2. Inequality joins use <, <=, >, and >= instead of ==. Can be used to restrict cross joins to create all possible combinations rather than all permutations. 3. Rolling joins are similar to inequality joins but only find the closest match. The most useful of these for us: we can join data to the nearest matching value. 4. Overlap joins are a special type of inequality join designed to work with ranges.


Handling missing data

Missing data is extremely common in ecological and biological data, and can arise for a ton of reasons. Learning how to find and handle missing data is an important part of data wrangling. First, let’s define the two different types of missing data, and then discuss how we might handle each type.

  1. Explicit missing values: These are easy - they’re missing values that we can see in our data (i.e., cell value for a variable is recorded as NA).
  2. Implicit missing values: These are a bit more pernicious, as the name suggests, we can’t see them, we simply have an entire row absent from the data.

Handling explicit missing values

There are many ways to handle these missing values, and it entirely depends on your dataset, question, and approach. Do NOT take these approaches as universally applicable! They’re simply common ways that missing data are dealth with in a variety of contexts.

Last observation carried forward: tidyr::fill()

When we are hand-recording data, we often won’t fill in every single value of a cell when those cells are simply duplicates of one another. For example, if we have multiple observations for each site and habitat type of a stream survey, we may only record the first row of each unique site/habitat type combination.

Replace NA with fixed value

Sometimes we don’t record data when we know it represents a fixed value, like 0. Or, we record some specific vlaue to represent an NA instead of NA or a blank cell (e.g., -999, ., etc.). In these instances we can use dplyr::coalesce() or dplyr::na_if() to replace the values.

# Replace NAs in count variable with 0
cleaned_stream_survey <- stream_survey |>
    fill(site_id, habitat_type, .direction = "down") |>
    mutate(count = coalesce(count, 0))

Missing or empty groups

With categorical (i.e., factor) data, sometimes we don’t have observations for particular groups, but we still want to display that missingness when we produce plots or other data summaries. To handle this, we can make use of the .drop argument in functions like group_by() and count(). In this example below, we have observations of pollinators taken in prairies, bee lawns, gardens, roadsides, and woodlands. When we count our data, note that woodland is missing because we have no observations for that group:

Working with string data: stringr package

There is a whole world of tools dedicated to working with string, or character data, mostly because of how infinitely complex it can become. As such, we can’t possibly do it justice in this course. For the most part, we’ll need just a handful of tools to work with strings that we might encounter in our data wrangling journey, so I’ve included some of the most useful functions below. The most challenging part of working with strings is getting a handle on regular expressions, which is the language we’ll need to use to recognize patterns in strings. We’ll only touch on this, and mostly use the stringr package out of the box in this course.

Refer to the stringr cheatsheet for more details on this package!

Most useful functions

Function What it does Example use Example syntax
str_detect() Finds whether a string contains a pattern Find all observations of Bombus species str_detect(species, "Bombus")
str_replace() Replaces the first occurrence of a pattern Standardize "B. impatiens" to "Bombus impatiens" str_replace(species, "B\\. impatiens", "Bombus impatiens")
str_replace_all() Replaces all occurrences of a pattern Standardize different spellings/capitalizations of "prairie" str_replace_all(habitat, "prairie|PRAIRIE", "Prairie")
str_extract() Extracts text matching a pattern Extract the year from a sample ID str_extract(sample_id, "20\\d{2}")
str_split() Splits a string into multiple pieces Separate "MN,StPaul,UMN" into individual components str_split(location, ",")


Working with date & time data: lubridate package

Working with dates and times is also a whole other kettle of fish given the complexities of physical phenomena and geopolitical nonsense (time zones, daylight savings, etc.). Just like with strings, my primary goal here is to introduce you to formatting dates and times correctly in R so that you can use the many lubridate functions to extract derivative values for your analysis (like day of the year, month, day, hour, etc.). The key is being able to convert your raw date or time data into a special class of atomic character data that are recognized and treated as dates and times.

For most folks, date will be the most common data you work with in this context, so we’ll start with that. The best place to handle converting your date data to date objects in R is during data import:

Once we have our date variables correctly specified and stored as date objects, we can easily do a whole bunch of math to get date differences, or extract various useful components like the ordinal date of the year. See the couple of examples below:

smammal_data |>

Modifying categorical data (i.e., factors): forcats package

Categorical variables are very common in biological data (think treatments, plots, or even years in some contexts), and we’ll need to know how to work with factors, which are the R lingo for categorical data. There’s two primary things we’ll need to know how to do with factors: (1) create factors, and (2) reorder them!

Converting data to factors

When we read data into R (as we discussed last week), R won’t automatically convert columns to factors unless we manually specify the atomic data type in our import function call. Instead, we will have to create factors by converting whatever data type we want to a factor. Any atomic data type can be converted into a factor. R accomplishes this by turning the data into a string (i.e., character data) and then to a factor. There are several functions to convert data to factors, including the base R factor() and forcats::fct(). Imagine we have some RNAseq data that we’ve imported:

processed_metadata <- RNAseq_metadata |>
    mutate(
      # Define strict biological ordinal progression
      disease_stage = factor(
        disease_stage, 
        levels = c("Stage I", "Stage II", "Stage III", "Stage IV"), 
        ordered = TRUE
    )
  )

Reordering factor levels

When we convert character or numeric data to factors, R will automatically create the levels according to alphanumeric sorting (that is, 0-9, A-Z, earliest date to latest date if working with datetime data). We can adjust this if there is an alternate order to our data. This is primarily important for when we plot our data (so that we can control which categories appear where in our plots), but can also matter for calculating summary statistics for tables and some analysis pipelines. Re-ordering our factors is called re-leveling. For example, imagine we have some data from an experiment where we measured gene expression of several genotypes:

gene_expression_df <- tibble(
  sample_id = paste0("S", 1:9),
  genotype = factor(c("gene_B", "gene_ctrl", "gene_A", 
                      "gene_B", "gene_ctrl", "gene_A", 
                      "gene_B", "gene_ctrl", "gene_A")),
  expression_level = c(12.4, 5.2, 8.1, 14.1, 4.9, 8.7, 11.8, 5.5, 9.0)
)

When R creates this factor variable, it levels the factors by alphanumeric order, making our control gene (gene_ctrl) the last level. That may be fine, but when we plot the data, we may prefer to have the control group display first to compare our other genotypes against it. To do that, we need to re-level the factors using fct_relevel(). Because we’re changing a vector of factors in our tibble, we use the fct_relevel() function inside our mutate function:

gene_expression_df <- gene_expression_df |>
    mutate(genotype = fct_relevel(genotype, c("gene_ctrl", "gene_A", "gene_B"))) # Here, we overwrite the order of the existing genotype factor

levels(gene_expression_df$genotype)
[1] "gene_ctrl" "gene_A"    "gene_B"
